# 功能 GDD 整合定稿工作流（SR-GDD-AI）

## 功能说明

**唯一输出：功能 GDD（定稿版，最终交付物）**。按本地 `resources/templates/feature-gdd.md` 模板产出实现粒度的功能开发文档（功能规则 Rn、界面流程、配置契约、多语言文本、验收标准 AC、交接清单），交给程序实现。

**主线定位（见 sr-askme 教学主线）**：本 skill 是**整合定稿步、最终交付物**——首选输入是 `sr-gdd-human` 的成稿（过程层工作文档，设计已审核确认）+ `/sr-config` 的配置表变更，产出**没有思考决策过程的干净 GDD** 交给程序。设计取舍、规则走向、界面细节已在 human 成稿阶段定过，本步**不推翻成稿口径**，只做格式化组装；发现成稿有设计问题时按「修订路由」处置，不静默改写。**直接调用**（只有旧案/配置表、无需先出可读版时）也可从零成稿，此时执行本文件全部流程。

**详细度铁律（本 skill 的核心标准）**：sr-gdd-ai 的产出是**交给程序的最终交付物**——只有设计结果与实现依据，没有思考决策过程。所有规则、界面、契约、验收写到程序可实现的粒度，不遗漏、不概括：

- **human 成稿**（直接调用外的首选输入）→ 规则与界面内容以它为基底逐章吸收，配置表变更 → 配置契约；成稿中的证据标注、假设/风险台账、设计核、治理引用等**过程信息不带入定稿**——它们留在成稿里供审核回溯；
- **直接调用路径**（从旧案/配置表起步）→ 拍板与取舍过程同样不入正文，关键决策只以"决议问答"的结论形态出现；
- 每个关键界面 → 单独 ASCII 线框图 + UE 交互标注 + 详细规则表（见模板 §5）；
- 数值 → 能引配置字段就引 `表名.字段名`，否则标"待配表"，不凭空写数。

宁可详尽，不要省略；宁可标注待确认，不要假装已定。

不提供一页设计 / 商业立项案等其它形态；商业 pitch 模板不得套给内部功能开发文档——历史教训：模板错配会让文档近半章节只能填占位，密度显著低于功能 GDD 结构。

不编造缺失的上游材料——缺什么就列出最小缺失清单，由人决定补不补。

## 使用方法

```
/sr-gdd-ai <主题或材料路径>
```

或直接说人话，例如"基于英雄改造v0.2.xlsx 出功能 GDD"、"把神话宝库的 human 成稿和配置变更整合成定稿"、"把《挂机战斗》的体验记录整理成策划案"。

## 无输入时的行为

裸调用时按 `../sr-askme/references/bare-invocation.md` 的共用纪律执行（说明输入、停下等待，不自行找题）。本 skill 收集：

1. **主题**：要写哪个功能的 GDD（功能名或一句话描述）。
2. **输入材料**（按主线性优先，有就给路径，没有就明说没有）：
   - **sr-gdd-human 成稿**（`<SR_WORKSPACE>\proposals\`，主线首选输入）
   - 配置表变更 / 建表记录（sr-config 产出或 .xlsx）
   - 旧策划案 / 脑图 / 提纲（`design\` 下或任意路径）——直接调用路径的输入
   - 体验记录 / 证据索引 / 竞品笔记（`<SR_WORKSPACE>\evidence\` 等）
   - UE/界面草稿、相关决议记录（`<SR_WORKSPACE>\decisions\`）

用户补齐后再从第 0 步开始。

提示时同时告知材料要求：**主线路径的最低输入是 sr-gdd-human 成稿 + 配置表变更**（配置变更没有就说明由谁补）；**直接调用路径**没有哪份上游材料是硬性必须的——最低输入是主题 + 能支撑规则粒度的描述（旧案、脑图、体验记录、配置表任一，或当场口述）；材料薄不阻塞，会触发第 2 步决议问答与 VOI 门判定。实际建议：**human 成稿（或同等详细度旧案）+ 涉及配置表**齐备时效率最高，可直接映射进功能规则和配置契约章节；缺了也能做，只是问答轮次会多。

## 路径约定

文中的 `<SR_WORKSPACE>`（产出落盘根目录）与 `<SR_PROJECT>`（Unity 工程根目录）在运行时从 `../sr-askme/config.local.json` 解析：文件不存在或字段为空时，先按 `../sr-askme/SKILL.md` 的首次配置引导收集并写入，再继续本流程；文件存在则直接采用，不再询问。本 skill 与 sr-askme 及其它 sr-* skill 为兄弟目录，须成组安装在同一 skill 根。

## 执行流程

### 第 0 步 · 载入项目语境

读 `../sr-askme/references/sr_project_context.md`，后续全程遵守其中的数值铁律与写作约束。
完成判据：已读完该文件。

### 第 1 步 · 资产盘点

列出用户提供的、以及 `<SR_WORKSPACE>\` 下已有的输入材料：**sr-gdd-human 成稿**（主线首选，`proposals\`）、配置表变更/建表记录、概念与玩家承诺、体验记录、证据索引、实验结果、竞品笔记、旧策划案、配置表（.xlsx）、生产约束。只盘点，不评价。输入含 human 成稿时，同时核对成稿章节能否支撑定稿（规则组、界面清单、验收标准、数值待定项齐全），缺项在第 2 步处理。
完成判据：产出一份材料清单（名称 + 路径），每项标注"已有 / 缺失"。

### 第 2 步 · 缺失上游检查（VOI 门 + 决议问答）

对每个缺失项问一个问题：**它的可能结果会改变决策、范围、投入或风险处置吗？**

- 会 → 列为"最小缺失 artifact"，向用户报告后**停下等补充**（除非用户明确说继续）
- 不会 → 标注"可选学习项"，不阻塞

缺失不是自动补材料的理由；写到"足够做决策"就停，不追求百科全书。输入为 human 成稿时，缺项多为"成稿未覆盖的留痕信息"（证据编号、假设来源），此类一律标"可选学习项"，不阻塞——过程留痕不在定稿中重建（见「详细度铁律」）；发现成稿有设计内容问题才按「修订路由」退回 sr-gdd-human。

**决议问答**：功能 GDD 要达到实现粒度（R 级规则、配置契约、AC），如果输入材料只有提纲级描述（如旧案 bullet、脑图）或 human 成稿缺章，先把会改变规则走向的关键取舍整理成**决议问题清单**（每条给候选方案 + 推荐 + 理由），请用户逐条拍板后再成稿。不替用户做设计取舍。
完成判据：每个缺失项都有 VOI 判定结论；若触发了决议问答，清单已获用户逐条拍板。

### 第 3 步 · 撰写

以 `resources/templates/feature-gdd.md` 为章节骨架依次撰写，按本目录 `references/evidence-boundary.md` 的证据纪律标注每个关键判断的来源标签，并遵守 sr_project_context.md 的数值铁律与四类陈述标注（此处不复述）。

**详细度要求（本步核心）**：
- **不遗漏**：成稿/旧案的全部设计结论（规则、界面、范围、验收）映射进 GDD 对应章节，成稿后逐项核对无遗漏；过程信息（证据、假设、拍板）留在成稿，不入正文；
- **human 成稿映射（主线路径）**：成稿的规则组（R1…）与界面章原样吸收为定稿对应章节的基底——规则内容不重写、口径不改动，只做两件事：①把配置表变更落成 §6 配置契约（字段/结构/状态）；②把成稿的机制表述对应到 `表名.字段名`，并把"数值待定项"升级为"已定值（标表字段）或待配表"，不保留两套口径。成稿的过程章（§0 来源/概念/设计核/台账/治理）**不带入定稿**；
- **界面章节**：模板 §5 必须为**每个关键界面**单独给出 ASCII 线框图（含布局、控件、UE 交互标注）+ UE 规则表（逐条编号 UE1…）+ 界面清单总览 + 流程 text 图 + 状态机（如适用）+ 全局交互规范；禁止只画一张总层级图敷衍；嵌套的解锁/失败分支/默认回退行为用**层级缩进列表**表达，不塞进大表格；
- **规则粒度**：每条 R 规则写到程序可实现的粒度，条件/动作/结果/边界齐全。

**证据纪律行内标注**（按 `references/evidence-boundary.md` 执行）：推断内容标 `【推断】`；未定项写 `待确认：<事项>`；引用真实配置标 `[真实]`、示例值标 `[示例]`，禁止把示例值写成真实值。

输入含旧策划案时，其内容映射进对应章节（功能详细 → 功能规则 Rn，配置表变更 → 配置契约），映射不了的差异点在文中标注。

上游材料含配置表（.xlsx）时，表内数值视作**修改或新增配置的来源**，可直接引用：标注 `表名.字段名` 并注明出自该 xlsx（状态为"待录入 `LuaConfigs` / `RPG_Configs`"），不再标"待配表"。xlsx 未覆盖的数值仍按数值铁律标"待配表"。
完成判据：模板每一节都有实质内容，或显式标注缺失原因（如"待配表""未决问题"）；无留空章节；**详细度核对通过：设计结论无遗漏，且正文无过程性内容**（无证据编号、无假设台账、无拍板记录）。

### 第 4 步 · 治理检查

过程留痕已由 sr-gdd-human 成稿承载（其 §0.9 治理引用已填写），本步仅复核成稿治理引用齐全且无占位符——定稿不设治理引用节，不在交付物中重复填写。
完成判据：主线（有成稿）时成稿治理引用五条齐全；直接调用路径无成稿时跳过本步，在 §0 内部留档注明。

### 第 5 步 · Human Gate

向用户呈现选项并等待选择，不替用户做批准类决定：

```
approve / approve_with_conditions / request_missing_evidence / revise / reject
```
完成判据：用户已从上述选项中明确选择其一；选择前不写决策记录。

用户选择后，按 `../sr-askme/references/decision-recording.md` 写决策记录（schema 见本目录 `references/decision.schema.json`）。`status` 映射：`approve→accepted`、`reject→rejected`、`approve_with_conditions→accepted`（条件写入选项备注）、`request_missing_evidence / revise→proposed`。

主线顺序是**先 human 后 ai**（见 sr-askme 教学主线）：`sr-gdd-human` 是**成稿步**——过程层工作文档（来源、概念种子、设计核、功能规则、界面流程、假设/风险台账、治理引用），供人审核确认，并向前供料 sr-config 落表；本 skill 是**整合定稿步、最终交付物**——把 human 成稿 + 配置表变更格式化为**没有思考决策过程的干净 GDD** 交给程序，配置契约与多语言文本在这里落成章节。两份文档职责不同、内容同源：定稿吸收成稿的结果章，成稿保留全部过程章。

本 skill 也可**直接调用**：只有旧案/配置表、不需要先出可读版时，直接从旧案起步执行本文件全部流程，跳过 human 版。
