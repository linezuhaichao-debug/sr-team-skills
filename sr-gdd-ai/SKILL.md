# 功能 GDD 整合定稿工作流（SR-GDD-AI）

## 功能说明

**唯一输出：功能 GDD 定稿**（最终交付物）。按 `resources/templates/feature-gdd.md` 产出实现粒度的功能开发文档，交给程序实现：功能规则 Rn、界面流程、§6 配置契约、§7 多语言文本、范围门、埋点、验收标准 AC、交接清单。

**详细度铁律**：定稿是**综合产物**——设计结果 + 配置落地 + 多语言文本；只写结果，不写整合过程。规则、界面、契约、验收写到程序可实现的粒度，不遗漏、不概括；数值以配置表实际落地为准标 `表名.字段名`，未落表的标"待配表"，不凭空写数。**宁可详尽标注待确认，不假装已定。**

**两条输入路径**：

- **主线路径**（首选）：输入 = `sr-gdd-human` 成稿（纯规则，设计已审核确认）+ `/sr-config` 的配置表（字段与记录已落）。本步把两侧**综合整合**——每条规则对应到配置表里实际落地的字段/记录，成稿 §11 的数值待定项落到实际配置，再据定稿生成多语言文案。
- **直接调用路径**：只有旧案/配置表、无需先出可读版时，从零执行本文件全部流程（含决议问答与全文撰写）。

**与成稿、配置表的分工、章节对应、两道门与退回方式：权威定义在 `../sr-askme/references/gdd-pipeline.md`**（第 0 步读入，本文件不复述）。一句话判据——成稿只有纯规则与设计（零配置指代）；配置字段由 `/sr-config` 从成稿规则派生；本步综合两侧整合成定稿并据定稿列出多语言文本条目。**整合只做一次**：定稿通过后成稿归档废弃，**定稿成为唯一的活文档**——后续设计微调、字段对应调整、文本改动都交 `sr-gdd-fix`（或直接编辑定稿）。本 skill 只负责首次整合。

不提供一页设计 / 商业立项案等其它形态；商业 pitch 模板不适配内部功能开发文档。不编造缺失的上游材料——缺什么就列最小缺失清单，由人决定补不补。

## 使用方法

```
/sr-gdd-ai <主题或材料路径>
```

或直接说人话，例如"基于英雄改造v0.2.xlsx 出功能 GDD"、"把神话宝库的成稿和配置变更整合成定稿"。

## 无输入时的行为

裸调用纪律见 `../sr-askme/references/bare-invocation.md`。本 skill 收集：

1. **主题**：要首次定稿哪个功能的 GDD。**若该功能已有定稿**，说明这是修改任务，请用户改用 `/sr-gdd-fix`（本 skill 只做首次整合）。
2. **输入材料**（有就给路径，没有就明说没有）：
   - **sr-gdd-human 成稿**（`<SR_WORKSPACE>\proposals\`，首次定稿的主线首选输入）
   - 配置表 / 建表记录（`/sr-config` 产出或 .xlsx）
   - 旧策划案 / 脑图 / 提纲（直接调用路径的输入）
   - 体验记录 / 证据索引 / 竞品笔记（`<SR_WORKSPACE>\evidence\` 等）
   - UE/界面草稿、相关决议记录（`<SR_WORKSPACE>\decisions\`）

提示时同时告知材料要求：**首次定稿的最低输入是成稿 + 配置表**（配置没有就说明由谁补）；**直接调用路径**没有硬性必须的上游材料，最低输入是主题 + 能支撑规则粒度的描述（旧案、脑图、体验记录、配置表任一，或当场口述）。材料薄不阻塞，问答轮次会相应增多。用户补齐后再从第 0 步开始。

## 路径约定

文中的 `<SR_WORKSPACE>`（产出落盘根目录）与 `<SR_PROJECT>`（Unity 工程根目录）在运行时从 `../sr-askme/config.local.json` 解析：文件不存在或字段为空时，先按 `../sr-askme/SKILL.md` 的首次配置引导收集并写入，再继续本流程；文件存在则直接采用，不再询问。本 skill 与 sr-askme 及其它 sr-* skill 为兄弟目录，须成组安装在同一 skill 根。

## 执行流程

### 第 0 步 · 载入项目语境与撰写纪律

读四份文件：`../sr-askme/references/sr_project_context.md`（数值铁律与写作约束）、`../sr-askme/references/gdd-pipeline.md`（三份产出契约与退回方式）、`../sr-askme/references/gdd-writing-discipline.md`（D1–D11 撰写纪律，本 skill 按适用项自查）、`../sr-askme/references/evidence-boundary.md`（只用其中「轻量标注」一段）。
完成判据：语境已生效——定稿每个数值标 `表名.字段名` 或"待配表"，§7 只收普通文本条目，正文不带过程留痕（核对点：第 3 步）。

### 第 1 步 · 资产盘点

列出用户提供的、以及 `<SR_WORKSPACE>\` 下已有的输入材料：**sr-gdd-human 成稿**（主线首选，`proposals\`）、配置表变更/建表记录、概念与玩家承诺、体验记录、证据索引、旧策划案、配置表（.xlsx）、生产约束。只盘点，不评价。

输入含成稿时，同时核对成稿能否支撑定稿（下列为**成稿章号**）：§4 规则组、§5 界面清单、§6 范围门、§9 验收标准、§11 数值待定项、附录 A（A.1–A.9，含 A.9 治理引用）齐全。缺项在第 2 步分类处置。
完成判据：产出一份材料清单（名称 + 路径），每项标注"已有 / 缺失"。

### 第 2 步 · 缺失上游检查（VOI 门 + 决议问答）

对每个缺失项问一个问题：**它的可能结果会改变决策、范围、投入或风险处置吗？**

- 会 → 列为"最小缺失 artifact"，向用户报告后**停下等补充**（除非用户明确说继续）
- 不会 → 标注"可选学习项"，不阻塞

缺失不是自动补材料的理由；写到"足够做决策"就停。

**按路径分流缺项**：

- **主线路径（输入含成稿，且成稿仍是活文档）**：
  - 缺的是**留痕信息**（证据编号、假设来源、拍板记录）→ 一律标"可选学习项"，不阻塞。过程留痕不在定稿中重建。
  - 缺的是**设计内容**（规则组/界面/范围/验收有缺口，或规则自相矛盾、机制对应不到配置字段）→ 走「修订路由」：按 `gdd-pipeline.md` 第四节输出修订点清单、run 置 `BLOCKED`，退回 `sr-gdd-human` 定向修订。**本步不替用户拍设计取舍。**
- **改已有定稿**：不属于本 skill——转告用户改用 `/sr-gdd-fix`（它按撰写纪律做影响面闭合与最小编辑）。
- **直接调用路径（无成稿）**：材料只有提纲级描述（旧案 bullet、脑图）时，把会改变规则走向的关键取舍整理成**决议问题清单**（每条给候选 + 推荐 + 理由），请用户逐条拍板后再成稿。不替用户做设计取舍。

完成判据：每个缺失项都有 VOI 判定结论并归入上面某一条分支；若触发了决议问答，清单已获用户逐条拍板。

### 第 3 步 · 撰写与整合

以 `resources/templates/feature-gdd.md` 为章节骨架依次撰写：**首次定稿**按 `gdd-pipeline.md` 第二节的章节对应表整合（该表第 0 步已读入，此处不复述），**直接调用路径**按同一骨架从零撰写。产出按 `../sr-askme/references/gdd-writing-discipline.md` 的适用项自查（D1–D9）。

整合时只需盯住三件事：

1. **规则与字段的对应**：§4 每条规则对应到配置表里实际落地的字段/记录，规则组号沿用成稿；对应不上的在 §6 状态列标"待配表"，不自行发明配置项。
2. **§6 配置契约从配置表读回**：中文字段 / 英文字段 / 结构 / 含义 / 状态（已有、新增、新增命名待定、待配表）。
3. **§7 多语言文本只列普通文本条目**（键 + 中文文案 + 状态），本步到此为止——**文本表的增删改由用户自行发起**，本 skill 不调用落表工具。GID 名称/描述键 `n{gid}`/`d{gid}` 不在此列（两类多语言的区分见 `../sr-askme/references/sr_project_context.md`）。

**详细度要求（本步核心）**：

- **不遗漏**：成稿/旧案的全部设计结论（规则、界面、范围、验收）映射进定稿对应章节，成稿后逐项核对；
- **界面章节**：为**每个关键界面**单独给出 ASCII 线框图（布局 + 控件 + UE 交互标注）+ UE 规则表（逐条编号 UE1…）+ 界面清单总览 + 流程 text 图 + 状态机（如适用）+ 全局交互规范；层级总图代替不了单界面图；嵌套的解锁/失败分支/默认回退用层级缩进列表；
- **规则粒度**：每条 R 规则条件/动作/结果/边界齐全，程序可直接实现；
- **正文行内标注**（按 `evidence-boundary.md` 的「轻量标注」）：推断内容标 `【推断】`；未定项写 `待确认：<事项>`；引用真实配置标 `[真实]`、示例值标 `[示例]`，示例值不冒充真实值。来源标签、Evidence Ledger、假设/风险台账属于过程留痕，只留在成稿。

输入含配置表（.xlsx）时，表内数值视作**修改或新增配置的来源**，可直接引用：标注 `表名.字段名` 并注明出自该 xlsx（状态为"待录入 `LuaConfigs` / `RPG_Configs`"）。xlsx 未覆盖的数值按数值铁律标"待配表"。
完成判据：模板每一节都有实质内容，或显式标注缺失原因（如"待配表""待确认"）；**设计结论无遗漏，且正文无过程性内容**（无证据编号、无假设台账、无拍板记录）。

### 第 4 步 · 治理复核

过程留痕由成稿附录 A 承载。本步只复核成稿 A.9 治理引用五条齐全、无占位符；定稿不设治理引用节，不在交付物中重复填写。
完成判据：主线路径下 A.9 五条齐全；直接调用路径无成稿时，按 `../sr-askme/references/governance-check.md` 复核五条，结论写进定稿 §0 内部留档（不写入交付正文）。

### 第 5 步 · Human Gate

向用户呈现定稿，**并突出整合结果**（规则与配置字段的对应、§6 配置契约、§7 多语言文本），等待选择：

```
approve / approve_with_conditions / request_missing_evidence / revise / reject
```
完成判据：用户已从上述选项中明确选择其一，且已就整合结果表态；选择前不写决策记录。**通过（approve / approve_with_conditions）即成稿生命周期结束**：成稿归档废弃，此后修改直接落定稿。

用户选择后按 `../sr-askme/references/decision-recording.md` 写决策记录。`status` 映射：`approve→accepted`、`approve_with_conditions→accepted`（条件写入选项备注）、`request_missing_evidence / revise→proposed`、`reject→rejected`。

## 产出规范

| 产出 | 路径（`<SR_WORKSPACE>\` 下） |
|------|------|
| 功能 GDD 定稿 | `proposals\<主题>_<日期>_定稿.md` |
| 修订点清单（仅退回成稿时） | `proposals\<主题>_<日期>_修订点.md` |
| 决策记录 | `decisions\decision_<主题>_<日期>.json` |

目录不存在时直接创建。日期格式 `YYYYMMDD`。定稿文件名带 `_定稿` 后缀，与同日成稿并存不覆盖。
