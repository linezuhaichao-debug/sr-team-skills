# 功能 GDD 定稿修改工作流（SR-GDD-FIX）

## 功能说明

**唯一输出：改后的定稿**（改动清单随决策记录留档）。定稿通过后成稿归档、定稿成为唯一活文档，此后所有改动都由本 skill 落在定稿上（归属见 `../sr-askme/references/gdd-pipeline.md`）。

- **不重跑整合**：只改用户指定的范围 + 影响面扫描（按纪律文件「影响面闭合」条目）扫出的受影响条目，不重新生成整份定稿、不回到 `sr-gdd-ai`。
- **不降低纪律**：修改与撰写吃同一套「撰写纪律」（`../sr-askme/references/gdd-writing-discipline.md`），大改动逐条自查。
- **配置侧不自己改表**：需要动配置表时调 `/sr-config`；改表后的定稿同步（§4 对应行、§6 契约）由它按自己的第 5 步完成。
- **文本不落表**：§7 只维护条目；文本表的增删改由用户自行发起。

形态基准：`../sr-gdd-ai/resources/templates/feature-gdd.md`（定稿骨架，本 skill 不重排结构）。原地修改当前定稿时沿用顶部 `status: active`；用户要求留版本时，新文件为 `active`，旧文件为 `archived`。

## 使用方法

```
/sr-gdd-fix <定稿路径> <要改什么>
```

或直接说人话，例如"把神话宝库定稿里每日次数从 3 次改成 5 次"、"给星海远征定稿补一个失败分支"。

## 无输入时的行为

裸调用纪律见 `../sr-askme/references/bare-invocation.md`。本 skill 收集：

1. **定稿路径**：要改哪份定稿（`<SR_WORKSPACE>\proposals\<主题>_<日期>_定稿.md`；只给主题时在 `proposals\` 下定位，多份候选项列给用户选，不默认取最新）。
2. **要改什么**：一句话说清改动意图（哪条规则 / 哪个界面 / 哪个字段 / 哪段文本）。
3. **状态**：目标文件顶部必须是 `status: active`；`provisional` / `blocked` 文档先回 `/sr-gdd-ai` 补齐，未写状态的旧文档先让用户确认其是否为当前有效定稿。

用户补齐后再从第 0 步开始。

## 路径约定

`<SR_WORKSPACE>` / `<SR_PROJECT>` 取自 `../sr-askme/config.local.json`；字段缺失、为空或路径失效时运行 `/sr-askme` 补齐；成组安装见 `../sr-askme/SKILL.md` §四。

## 执行流程

### 第 0 步 · 载入项目语境与撰写纪律

读 `../sr-askme/references/sr_project_context.md`（数值铁律与写作约束）、`../sr-askme/references/gdd-pipeline.md`（三份产出契约与改动归属）、`../sr-askme/references/gdd-writing-discipline.md`（撰写纪律，按其「适用」列取定稿侧条目）、`../sr-askme/references/evidence-boundary.md`（只用「轻量标注」一段）。
完成判据：语境已生效——改动涉及的数值按 `sr_project_context.md`「数值状态词」标 `表名.字段名` 或"待配表"，正文只留当前口径（核对点：第 5 步复核清单）。

### 第 1 步 · 读定稿、锁定改动

先读定稿顶部 `status`。若为 `provisional` 或 `blocked`，停止并转回 `/sr-gdd-ai`；若缺少 `status`，停止并请用户确认它是否是当前有效定稿，确认后本次保存才补 `status: active`。只有 `active` 文档继续：读全文，把改动意图落到具体条目上（哪几条 R、哪个界面 / UE、哪个字段、哪段文案），并记下改动前的原口径（改动清单要用）。意图含糊时一次问清，不自行扩大范围。
完成判据：目标文档已确认是 `active`（或用户已确认无状态旧文档为当前定稿并将在本次保存补标），改动点逐条落到"章节 + 条目"级别，并已向用户复述确认。

### 第 2 步 · 影响面扫描

对每个改动点扫一遍受影响面（范围按纪律文件「影响面闭合」条目），产出**改动清单**（第 4 步照它改、第 5 步照它复核、第 6 步呈现并随决策记录留档——**不单独落 md，写进 `decision_result.changes`**）：

| 编号 | 改动点 | 涉及章节 | 连带影响 | 是否动配置表 | 处置 |
| --- | --- | --- | --- | --- | --- |

连带影响至少扫这些：规则 ↔ 界面 UE ↔ 范围门 ↔ 埋点 ↔ 验收标准 ↔ §6 字段对应 ↔ §7 多语言文本。扫到的项要么进清单，要么明确写"已核，不受影响"。
完成判据：每个改动点的连带影响都有结论；清单覆盖全部需要改的条目，无"待定"。

### 第 3 步 · 配置侧（需要动表时）

改动需要新增 / 修改字段或数值时，**调 `/sr-config` 改表**——它按最小事务写入、读回验收，并顺手回写定稿 §4 对应行与 §6 契约。本 skill 不直接改工作簿。不涉及配置表时跳过本步并记"无需改表"。
完成判据：涉及配置表时 `/sr-config` 已 `PASS`（或明确列为阻断项并向用户报告）。

### 第 4 步 · 改定稿

按改动清单改定稿，执行撰写纪律的定稿侧适用项（条目内容与判据以 `../sr-askme/references/gdd-writing-discipline.md` 为准，此处不复制编号）：

- **最小编辑**：只动清单里的条目，不顺手重写、不重排章节、不改与本次无关的规则；
- **编号与术语**：沿用既有 R 组号、界面 ID（UI-Mx）、UE 编号（UEx）与术语；新增条目接在所属组末尾；
- **口径**：正文只留改后的当前口径（取代关系进改动清单，按纪律文件「当前口径」条目）；
- **数值**：落地值标 `表名.字段名`，未落表标"待配表"（按纪律文件「数值」条目定稿侧变体）。
完成判据：改动清单逐条落地；正文口径统一、无新旧对照；编号与术语无冲突。

### 第 5 步 · 复核

通读改动范围与受影响章节。纪律类逐项（规则写法、配置指代、数值标注、口径、界面、标注、术语）按 `../sr-askme/references/gdd-writing-discipline.md` 定稿侧适用项核对；另核本 skill 特有项：

- [ ] 改动清单每条都已落地，无漏改、无超范围改动
- [ ] 影响面全部闭合（规则 / 界面 / 范围门 / 埋点 / 验收 / §6 / §7）
- [ ] 定稿结构未变（章节顺序与骨架与 `feature-gdd.md` 一致）
- [ ] 定稿顶部 `status` 保持 `active`；用户要求留版本时，新文件为 `active`、旧文件为 `archived`

完成判据：清单全部通过；不过关则修订后复查。用户需要独立复核时，可在本步之后调 `/sr-gdd-review` 复审（它按"定稿改过之后"分诊）。

### 第 6 步 · Human Gate

向用户呈现**改动清单（改前 → 改后）+ 改后的受影响章节**，等待选择：

```
approve / revise / reject
```
完成判据：用户已从上述选项中明确选择其一；选择前不写决策记录。

本 skill 不设 `request_missing_evidence`——输入就是定稿本身，缺什么在第 1 步已问。用户选择后按 `../sr-askme/references/decision-recording.md` 写决策记录，**把改动清单写进 `decision_result.changes`**（数组，每条：编号 / 改动点 / 涉及章节 / 改前 → 改后 / 是否动配置表）；留版本时把新旧定稿路径写进 `decision_result.files`。`status` 映射：`approve→accepted`、`revise→proposed`、`reject→rejected`。

## 产出规范

| 产出 | 路径（`<SR_WORKSPACE>\` 下） |
|------|------|
| 改后的定稿（**原地更新**，维持唯一活文档） | `proposals\<主题>_<日期>_定稿.md` |
| 改动清单 | **不单独落盘**——写进决策记录的 `decision_result.changes` |
| 决策记录 | `decisions\decision_<主题>_<日期>.json` |

日期格式 `YYYYMMDD`。用户要求留版本时，定稿另存为 `<主题>_<新日期>_定稿.md`，新旧路径写进决策记录的 `decision_result.files`。
