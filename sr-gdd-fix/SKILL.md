# 功能 GDD 定稿修改工作流（SR-GDD-FIX）

## 功能说明

**唯一输出：改后的定稿**（改动清单随决策记录留档）。定稿通过后成稿归档、定稿成为唯一活文档，此后所有改动都由本 skill 落在定稿上（归属见 `../sr-askme/references/gdd-pipeline.md`）。

- **不重跑整合**：只改用户指定的范围 + 影响面扫描（D11）扫出的受影响条目，不重新生成整份定稿、不回到 `sr-gdd-ai`。
- **不降低纪律**：修改与撰写吃同一套「撰写纪律」（`../sr-askme/references/gdd-writing-discipline.md`），大改动逐条自查。
- **配置侧不自己改表**：需要动配置表时调 `/sr-config`；改表后的定稿同步（§4 对应行、§6 契约）由它按自己的第 5 步完成。
- **文本不落表**：§7 只维护条目；文本表的增删改由用户自行发起。

形态基准：`../sr-gdd-ai/resources/templates/feature-gdd.md`（定稿骨架，本 skill 不重排结构）。

## 使用方法

```
/sr-gdd-fix <定稿路径> <要改什么>
```

或直接说人话，例如"把神话宝库定稿里每日次数从 3 次改成 5 次"、"给星海远征定稿补一个失败分支"。

## 无输入时的行为

裸调用纪律见 `../sr-askme/references/bare-invocation.md`。本 skill 收集：

1. **定稿路径**：要改哪份定稿（`<SR_WORKSPACE>\proposals\<主题>_<日期>_定稿.md`；只给主题时在 `proposals\` 下定位，多份候选项列给用户选，不默认取最新）。
2. **要改什么**：一句话说清改动意图（哪条规则 / 哪个界面 / 哪个字段 / 哪段文本）。

用户补齐后再从第 0 步开始。

## 路径约定

文中的 `<SR_WORKSPACE>`（产出落盘根目录）与 `<SR_PROJECT>`（Unity 工程根目录）在运行时从 `../sr-askme/config.local.json` 解析：文件不存在或字段为空时，先按 `../sr-askme/SKILL.md` 的首次配置引导收集并写入，再继续本流程；文件存在则直接采用，不再询问。本 skill 与 sr-askme 及其它 sr-* skill 为兄弟目录，须成组安装在同一 skill 根。

## 执行流程

### 第 0 步 · 载入项目语境与撰写纪律

读 `../sr-askme/references/sr_project_context.md`（数值铁律与写作约束）、`../sr-askme/references/gdd-pipeline.md`（三份产出契约与改动归属）、`../sr-askme/references/gdd-writing-discipline.md`（D1–D11）、`../sr-askme/references/evidence-boundary.md`（只用「轻量标注」一段）。
完成判据：语境已生效——改动涉及的数值标 `表名.字段名` 或"待配表"，正文只留当前口径（核对点：第 5 步复核清单）。

### 第 1 步 · 读定稿、锁定改动

读定稿全文，把改动意图落到具体条目上（哪几条 R、哪个界面 / UE、哪个字段、哪段文案），并记下改动前的原口径（改动清单要用）。意图含糊时一次问清，不自行扩大范围。
完成判据：改动点逐条落到"章节 + 条目"级别，并已向用户复述确认。

### 第 2 步 · 影响面扫描（D11）

对每个改动点扫一遍受影响面，产出**改动清单**（第 4 步照它改、第 5 步照它复核、第 6 步呈现并随决策记录留档——**不单独落 md，写进 `decision_result.changes`**）：

| 编号 | 改动点 | 涉及章节 | 连带影响 | 是否动配置表 | 处置 |
| --- | --- | --- | --- | --- | --- |

连带影响至少扫这些：规则 ↔ 界面 UE ↔ 范围门 ↔ 埋点 ↔ 验收标准 ↔ §6 字段对应 ↔ §7 多语言文本。扫到的项要么进清单，要么明确写"已核，不受影响"。
完成判据：每个改动点的连带影响都有结论；清单覆盖全部需要改的条目，无"待定"。

### 第 3 步 · 配置侧（需要动表时）

改动需要新增 / 修改字段或数值时，**调 `/sr-config` 改表**——它按最小事务写入、读回验收，并顺手回写定稿 §4 对应行与 §6 契约。本 skill 不直接改工作簿。不涉及配置表时跳过本步并记"无需改表"。
完成判据：涉及配置表时 `/sr-config` 已 `PASS`（或明确列为阻断项并向用户报告）。

### 第 4 步 · 改定稿

按改动清单改定稿，执行撰写纪律的适用项（D1–D6、D8、D9 为主，D11 保证影响面闭合）：

- **最小编辑**：只动清单里的条目，不顺手重写、不重排章节、不改与本次无关的规则；
- **编号与术语**：沿用既有 R 组号、界面 ID（UI-Mx）、UE 编号（UEx）与术语；新增条目接在所属组末尾；
- **口径**：正文只留改后的当前口径（取代关系进改动清单，D4）；
- **数值**：落地值标 `表名.字段名`，未落表标"待配表"（D3）。
完成判据：改动清单逐条落地；正文口径统一、无新旧对照；编号与术语无冲突。

### 第 5 步 · 复核

通读改动范围与受影响章节，逐项核对：

- [ ] 改动清单每条都已落地，无漏改、无超范围改动
- [ ] 影响面全部闭合（规则 / 界面 / 范围门 / 埋点 / 验收 / §6 / §7）
- [ ] 规则仍一句话可读、编号仍是组级（D1）
- [ ] 规则正文只有设计语言，配置对应只在「配置字段」列与 §6（D2）
- [ ] 数值都标了 `表名.字段名` 或"待配表"（D3）
- [ ] 无"曾经 / 原先 / 改动前"式表述（D4）
- [ ] 受影响界面仍有线框图 + UE 表，新增 / 改动的 UE 已编号（D5）
- [ ] 新增判断有 `【推断】` / `待确认：` 标注（D8）
- [ ] 术语全文一致（D9）
- [ ] 定稿结构未变（章节顺序与骨架与 `feature-gdd.md` 一致）

完成判据：清单全部通过；不过关则修订后复查。

### 第 6 步 · Human Gate

向用户呈现**改动清单（改前 → 改后）+ 改后的受影响章节**，等待选择：

```
approve / revise / reject
```
完成判据：用户已从上述选项中明确选择其一；选择前不写决策记录。

本 skill 不设 `request_missing_evidence`——输入就是定稿本身，缺什么在第 1 步已问。用户选择后按 `../sr-askme/references/decision-recording.md` 写决策记录，**把改动清单写进 `decision_result.changes`**（数组，每条：编号 / 改动点 / 涉及章节 / 改前 → 改后 / 是否动配置表）；留版本时把新旧定稿路径写进 `decision_result.files`。`status` 映射：`approve→accepted`、`revise→proposed`、`reject→rejected`。

## 产出规范

| 产出 | 路径（`<SR_WORKSPACE>\` 下） |
|------|------|
| 改后的定稿（**原地更新**，维持唯一活文档） | `proposals\<主题>_<日期>_定稿.md` |
| 改动清单 | **不单独落盘**——写进决策记录的 `decision_result.changes` |
| 决策记录 | `decisions\decision_<主题>_<日期>.json` |

日期格式 `YYYYMMDD`。用户要求留版本时，定稿另存为 `<主题>_<新日期>_定稿.md`，新旧路径写进决策记录的 `decision_result.files`。
