# 功能 GDD 定稿审查工作流（SR-GDD-Review）

## 功能说明

**唯一输出：审查报告**。对 sr-gdd 系列产出的功能 GDD **定稿**做只读审查——结构骨架、撰写纪律、数值落地标注、配置契约与多语言文本、与成稿/配置表的整合一致性——落在 `proposals\<主题>_<日期>_审查.md`，供用户决定是否交程序。

- **只读，不改定稿**：管线里对定稿的改动统一由 `sr-gdd-fix` 承接（最小编辑 + 影响面闭合 + 决策记录，见 `../sr-askme/references/gdd-pipeline.md`），审查只负责发现问题并把证据写足，让修复能照单执行。用户确认修复后转 `/sr-gdd-fix`，不在本 skill 内动笔。
- **分层审查**：基础自检（V1–V9，定稿本体的写作纪律）+ 整合一致性（V10–V13，与成稿/配置表交叉核对）。整合层缺对照物（无成稿或无配置表）时只做能做的部分，缺什么在报告里写明"未核"，不算不通过。
- **不做设计改判**：规则好不好玩、数值合不合理不是审查对象；本 skill 查的是"这稿是否可交程序实现"。设计矛盾类发现只定位证据、交用户裁决。
- **不替定稿门背书**：定稿门（`approve`）只能由用户批；审查报告是质量意见，不是通过凭证。

## 使用方法

```
/sr-gdd-review <定稿路径或主题>
```

或直接说人话，例如"审查一下神话宝库的定稿"、"这份 GDD 能不能交给程序"。

## 无输入时的行为

裸调用纪律见 `../sr-askme/references/bare-invocation.md`。本 skill 收集：

1. **定稿**：路径或主题（只给主题时在 `<SR_WORKSPACE>\proposals\` 下定位；多份候选项列给用户选，不默认取最新）。没有定稿时停止，说明应先走 `/sr-gdd-ai`。
2. **对照物**（有就给路径，没有就明说没有；不影响开工，只影响整合层覆盖度）：对应成稿、配置表（.xlsx 或 `/sr-config` 产出记录）、相关决策记录。

## 路径约定

`<SR_WORKSPACE>` / `<SR_PROJECT>` 取自 `../sr-askme/config.local.json`；字段缺失、为空或路径失效时运行 `/sr-askme` 补齐；成组安装见 `../sr-askme/SKILL.md` §四。

## 执行流程

### 第 0 步 · 前置分诊

读定稿顶部 `doc_type` + `status`（两字段定义见 `gdd-pipeline.md` §一·补），按表分流：

| doc_type | status | 处置 |
| --- | --- | --- |
| `final_gdd` | `pending` | 主线首次定稿待审查——ai 第 5 步的常规到达形态，全量审查。 |
| `final_gdd` | `active` | 当前生效定稿——独立调用或 fix 之后复审，全量审查；已有审查报告且此后未再改动时先问是否重跑。 |
| `final_gdd` | `provisional` / `blocked` | 照常审查，但报告开头注明"非主线 active 定稿，不能直接交程序；升级须补走 `sr-gdd-human → /sr-config → sr-gdd-ai` 主线"。 |
| `final_gdd` | `archived` | 已被替代或废弃，不审查；请用户指认当前生效定稿。 |
| `draft_gdd` | 任意 | 不在本 skill 范围：成稿本有成稿门（`sr-gdd-human` 第 5 步），提示用户走那道门；用户坚持时才按本清单中适用成稿的项审查，并在报告注明审查口径。 |
| 无头部字段 | — | 请用户确认是否当前有效定稿；确认后照常审查，报告中注明"按用户确认视为定稿"。 |

完成判据：已读两字段并按表确定本次审查口径（pending 全量 / active 复审询问 / 非主线注明 / 成稿转介 / 用户确认旧文档）。

### 第 1 步 · 载入项目语境与撰写纪律

读 `../sr-askme/references/sr_project_context.md`（数值状态词）、`../sr-askme/references/gdd-pipeline.md`（三份产出契约与章节对应表）、`../sr-askme/references/gdd-writing-discipline.md`（撰写纪律，取定稿侧适用项作审查基准）、`../sr-askme/references/evidence-boundary.md`（只用「轻量标注」一段）。
完成判据：审查基准已生效——每个数值知道该标什么，每章知道该长什么样。

### 第 2 步 · 盘点定稿与对照物

读定稿全文，盘点对照物：同主题成稿（`proposals\` 下无 `_定稿` 后缀文件）、配置表、相关决策记录（`decisions\`）。只盘点，不评价。
完成判据：报告"输入"节所需信息齐全（定稿路径与 status、各对照物有/无）。

### 第 3 步 · 基础自检（V1–V9）

对照检查表逐项核对定稿本体，每项记录 通过 / 不通过 + 证据（章节、原文定位）。发现不通过时不改文，把证据写足——定位到"章节 + 条目 + 原文"级别，让 `/sr-gdd-fix` 能直接照单修复。
完成判据：V1–V9 每项有结论。

### 第 4 步 · 整合一致性（V10–V13）

V11、V13 不依赖对照物，总要核；其余按对照物覆盖：

- 有成稿 → V12：按 `gdd-pipeline.md` 第二节章节对应表逐项核对，成稿设计结论无遗漏落进定稿，验证计划与已废弃口径正确地**未**进定稿；
- 有配置表 → V10 全查 + V5 抽查落地：标注 `表名.字段名` 的字段在表里真实存在、取值不冲突，§6 契约与实际字段一致；
- 缺对照物的项标"未核（缺对照物）"，不算不通过。
完成判据：V10–V13 每项有结论或明确标注未核原因。

### 第 5 步 · 出报告并交给用户

按输出格式写报告落盘，向用户呈现结论与阻塞项，并说明三条去路：用户自行处理 / 转 `/sr-gdd-fix` 按问题清单修复（配置表问题转 `/sr-config`）/ 争议项当面裁决。本 skill 不写决策记录——审查不改变定稿。
完成判据：报告已落盘到 `proposals\<主题>_<日期>_审查.md`；V1–V13 每项有结论或"未核 + 原因"；阻塞项已逐条点到"章节 + 条目 + 原文"；三条去路已向用户说明。

## 检查表

对每项输出：通过 | 不通过 + 证据（章节/原文定位）。标注（D<n>）的项，判据以 `../sr-askme/references/gdd-writing-discipline.md` 对应条目为准（含其「判据」列与成稿/定稿变体），本表只写查什么。

| ID | 项 | 查什么 |
|---|---|---|
| V1 | 状态与身份 | 顶部两字段合法且自洽：`doc_type: final_gdd`、文件名带 `_定稿` 后缀、`status` 在该 doc_type 的合法组内（`pending` / `active` / `provisional` / `blocked` / `archived`）；`provisional` / `blocked` 产物未被当作可交程序的正式定稿呈现 |
| V2 | 结构骨架 | 章节顺序与 `../sr-gdd-ai/resources/templates/feature-gdd.md` 骨架一致；不含成稿专属内容（验证计划章、已废弃口径章、附录 A 台账、证据编号、拍板记录等过程留痕） |
| V3 | 规则写法（D1） | 逐条对照 D1 判据查规则章：规则可读性、组级编号、交叉引用 |
| V4 | 语言分层（D2） | 逐条对照 D2 判据查配置指代：规则正文、「配置字段」列与 §6 各归各位 |
| V5 | 数值落地（D3） | 逐条对照 D3 判据（定稿侧变体）查每个数值的标注；有配置表时抽查标注的字段真实存在 |
| V6 | 当前口径（D4） | 逐条对照 D4 判据查历史性表述与新旧对照 |
| V7 | 界面章（D5/D6） | 逐条对照 D5、D6 判据查线框图、UE 表与归属边界声明 |
| V8 | 标注纪律（D8） | 逐条对照 D8 与 `evidence-boundary.md`「轻量标注」查标注：`【推断】`、`待确认：`、`[示例]` |
| V9 | 文本卫生（D9） | 逐条对照 D9 判据查术语一致性与过程叙事 |
| V10 | 配置契约 | §6 状态列取值合法（已有 / 新增 / 新增命名待定 / 待配表）；有配置表时与实际字段逐项核对一致 |
| V11 | 多语言文本 | §7 只列普通文本条目（键 + 中文文案 + 状态）；无 `n{gid}` / `d{gid}`（那两类随配置表 gid 走）；文案与规则口径一致 |
| V12 | 上游完整性（有成稿时） | 按 `gdd-pipeline.md` 章节对应表：成稿设计结论逐项落进定稿无遗漏；验证计划、§12、附录 A 正确地未进定稿；成稿状态为 `archived` |
| V13 | 整合自洽 | §4 规则 ↔ §6 字段 ↔ §7 文案互相可追溯；范围门、埋点、验收标准与规则不矛盾 |

## 输出格式

````markdown
GDD 定稿审查：<主题>

## 结论
可交程序 | 建议修复后交付 | 需用户裁决

## 输入
- 定稿：<路径>（status: …）
- 对照物：成稿（有/无）· 配置表（有/无）· 决策记录（有/无）

## 分层摘要
- 基础自检（V1–V9）：…
- 整合一致性（V10–V13）：…（缺哪项对照物写明）

## 问题列表
| ID | 位置 | 问题 | 建议 | 优先级 |
|---|---|---|---|---|
| V5 | §4 R2 | 概率只有裸数值，未标字段 | 补标 `表名.字段名` 或"待配表" | 阻塞 |

## 已通过项
- V2 …
````

结论判据：有阻塞级问题 → **建议修复后交付**；只有设计取舍、数值真源冲突等须用户拍板的问题 → **需用户裁决**；全过 → **可交程序**。`provisional` / `blocked` 定稿无论结论如何，报告开头保留前置分诊的注明。阻塞 / 非阻塞分档在问题列表优先级列体现。
